# Security review, November 2026

A source review of Norn at `55518dd` (1.0.0-rc.1 plus fixes), done on macOS. It reports
what was checked and how. It is one reviewer's reading, not an external audit, and
nothing here was penetration-tested or fuzzed. "Read" below means the source was read;
"ran" means a test or tool was run on this machine.

Line numbers are of the tree with the fixes applied.

## Threat model

| Actor | Assumed able to | Norn's position |
| --- | --- | --- |
| Another local user | Run any program, reach loopback TCP, list `/tmp` | Must get nothing, unless the operator turned on a TCP or HTTP listener (F4, F5) |
| A process of the daemon's user | Everything the daemon's files and sockets allow, signal it, read its memory | Trusted. Norn cannot defend against it; SECURITY.md says so |
| A connected client | Send any bytes on the socket | May be buggy or hostile, and must not exhaust or crash the daemon |
| A web page in a local browser | Send requests to loopback addresses | Must not reach MCP over HTTP (F3) |
| A malicious file on import | Whatever its bytes can do to `nornctl` | Runs in the client process, not the daemon; a bad file must only fail that import |
| Someone with the data files | Read and change them while Norn is stopped | Damage is detected, not forgery, unless encrypted; see [storage.md](../reference/storage.md#encryption) |
| A process sharing the rings | Write into iceoryx2's bookkeeping | Same user only, and off by default; SECURITY.md covers it |

## Findings

Severity is impact on the threat model above. Status is what happened in this tree.

| # | Severity | Finding | Where | Status |
| --- | --- | --- | --- | --- |
| F1 | Medium | The database directory was created under the umask, so on a typical `022` system any local user could read every segment and the metadata log | `crates/server/src/daemon/router.rs:72`, `crates/storage/src/platform/unix.rs` | Fixed |
| F2 | Medium | An MCP Unix socket had no directory check: the daemon's `Server::bind` covered only the gRPC endpoint, and runtime-rs uses an existing directory as it finds it. SECURITY.md's "refuses a more open directory" was untrue of it. Relative paths and remote pipe names were also accepted | `crates/server/src/daemon/claim.rs`, `crates/server/src/config/mcp.rs` | Fixed |
| F3 | Medium | MCP over HTTP checked `Host` but not `Origin`. A request with `Origin: https://evil.example` got 200 when run without the fix | `crates/server/src/mcp/transport.rs:59` | Fixed |
| F4 | Medium | `listen = "tcp:..."` gives every local user full read and write, with no identity check. The docs call it a test fallback, but a configuration can use it | `crates/transport/src/endpoint.rs:131`, `crates/server/src/config/mod.rs:142` | **Mitigated, not removed**: an explicit warning at every start. Owner decision below |
| F5 | Medium | `--mcp http:` has no authentication: every local user can read through the tools. Documented, opt-in, loopback only | `crates/server/src/config/mcp.rs`, `crates/server/src/config/mod.rs:142` | **Mitigated, not removed**: the same warning. Owner decision below |
| F6 | Medium | New directories were not durable: `StreamWriter::open` synced only the immediate parent, and `Registry::open` none, so a power cut could lose a new stream's or database's directory entries, and with them segments already fsynced and acknowledged `DURABLE` | `crates/storage/src/platform/mod.rs`, `crates/storage/src/stream.rs`, `crates/metadata/src/registry/mod.rs` | Fixed. Found by reading; the loss itself was not reproduced, which would need a power-cut harness |
| F7 | Medium | The socket directory rule assumed "a 0700 directory we can use is ours". Root can use another user's, and a symbolic link in `/tmp` passed the check, because `metadata` follows it | `crates/transport/src/platform/unix/socket_file.rs:34`, `:85` | Fixed. The symlink case ran; the root case has no test, since it needs running as root |
| L1 | Low | No disk budget. A client can write until the disk is full; retention limits it only if a policy is set. Behaviour on `ENOSPC` was not tested | no code exists; `crates/storage/src/retention.rs` is the nearest | Open |
| L2 | Low | MCP's HTTP sessions have no count limit: runtime-rs uses `LocalSessionManager::default()`, idle for 300 s. MCP replay sessions are bounded, and bodies are limited to 4 MiB by rmcp, but a client can open sessions repeatedly | `runtime-rs agents/src/mcp/serve.rs:73` | Open, upstream. Not measured |
| L3 | Low | Exports are created under the umask, so they may be readable by others, including from an encrypted store | `crates/cli/src/transfer.rs:99` | Open; documented |
| L4 | Low | Sidecars and logs are read whole or at lengths they record, trusting only a CRC, so a tampered file can force a large allocation. Requires write access to the data | `crates/index/src/detail/store.rs:112`, `crates/index/src/summary.rs:96`, `crates/metadata/src/log/mod.rs` | Open |
| L5 | Low | The claim-then-bind in `Daemon::bind` leaves a window between the check and the real bind. Only the directory's owner can change it in that window, and that user is trusted | `crates/server/src/daemon/claim.rs` | Accepted |
| L6 | Low | Atomic writes use a fixed `.tmp` name and follow a symbolic link there. Only reachable by a same-user process, now that F1 closes the directory | `crates/storage/src/fsio.rs:87` | Open |
| L7 | Low | Quarantine only grows, and nothing bounds it. A tampered store could fill the disk at recovery by at most its own size | `crates/storage/src/recovery/quarantine.rs` | Open |

### Owner decision: F4 and F5

A warning does not close these. The listeners remain usable by every local user once
an operator turns them on. Closing them needs either a token on those transports, or
refusing them unless a setting acknowledges the exposure, and either changes how
existing configurations start. That is a product decision before 1.0, not a bug fix,
so it was left open. Until then: neither is a default, and both are logged at `WARN`.

### Fixes and their tests

| Finding | Fix | Regression test (all ran and passed) |
| --- | --- | --- |
| F1 | `secure_database_dir`: creates `0700`, or tightens an existing directory and logs its old mode, so a store from 1.0.0-rc.1 keeps working | `crates/server/tests/exposure.rs` `the_database_directory_is_closed_to_other_users_new_or_not` |
| F2 | `claim_endpoints` holds every local MCP endpoint to the gRPC checks; `McpTransport` parses through `Endpoint` | `exposure.rs` `an_mcp_socket_in_a_directory_others_can_enter_stops_the_start`; `mcp_config.rs` `a_relative_socket_or_a_remote_pipe_is_refused` |
| F3 | `allowed_origins`: loopback, and `https://` plus each of `[mcp] hosts`. No `Origin` still passes: browsers always send one | `exposure.rs` `a_web_page_cannot_call_mcp_on_loopback_and_an_agent_still_can`, confirmed failing (200, not 403) with the fix removed |
| F4, F5 | `DaemonConfig::exposures`, logged by `claim_endpoints` | `mcp_config.rs` `what_any_local_user_could_reach_is_named` |
| F6 | `create_dir_durable`, and the same in the registry | `platform::tests::every_new_directory_has_its_parent_synced_and_old_ones_are_left_alone`, which checks what is synced, not a power cut. The registry's version has no test of its own |
| F7 | `prepare_directory` refuses a symbolic link; `check_owner` compares owners after the bind | `crates/transport/tests/unix_socket.rs` `a_symlinked_socket_directory_is_refused_and_nothing_is_made_beyond_it` |

## What was examined

**Listeners.** Read: `crates/transport/src/platform/unix.rs`, `unix/socket_file.rs`,
`endpoint.rs`, `tcp.rs`, `incoming.rs`, `limits.rs`, `crates/server/src/daemon/serve.rs`,
`reflection.rs`, `crates/server/src/mcp/{endpoint,transport,sessions,dial}.rs`, and
runtime-rs's `agents/src/listen/sys/unix.rs`. The daemon binds through runtime-rs, not
`norn-transport`; `norn-transport` is only its pre-flight check, which is how F2 arose.
A default daemon opening no TCP port is asserted by the existing `mcp_surface.rs`.

**Windows named pipes.** Read only, in part: `windows.rs` and part of `windows/security.rs`
in `norn-transport`, and the outline of runtime-rs's `windows.rs`. Nothing was run on
Windows, and SECURITY.md's note that this code has not been run there still stands. The
database directory fix does nothing on Windows, where it relies on the inherited ACL;
whether that ACL is owner-only was **not checked**.

**Input and budgets.** Read: `metered.rs` and `metered/cost.rs` (not `reader.rs` or
`wire.rs` line by line), `query/token.rs`, `config/{engine,file,shared}.rs`,
`crates/codec/src/zstd.rs`, `crates/storage/src/format/*`, `segment/load.rs`, `scan.rs`,
`chunk/decode.rs`, `crates/metadata/src/log/replay.rs`. Limits on connections,
subscriptions and replay sessions were confirmed to be enforced at their call sites by
search, not by load testing. Query budgets were **not traced** end to end. HTTP/2 header
and frame limits, which are tonic's and hyper's, were **not examined**.

**Paths.** Stream directories are named from a numeric id
(`crates/storage/src/layout.rs`), so no client string reaches a path. No RPC takes a path.
Import and export paths are the client's, in its own process, and an export uses
`create_new`, which refuses an existing file or a symbolic link. Symbolic links inside
the data directory are followed; that is same-user only (L6).

**Malicious import files.** Read: the CSV line bound, the MCAP reader's options and
parts of the Parquet reader. Whether the `parquet`, `arrow` and `mcap` crates can panic or
over-allocate on crafted input was **not tested**. A failure would hit `nornctl`, not the
daemon, since all three run client-side. Fuzzing is outside this review.

**Durability.** Read: segment writer, seal, compaction commit, recovery, quarantine,
`atomic_write`, the journal's option handling, the metadata log's sync. Write-new,
rename, sync, delete-old ordering and the barrier before a seal hold as documented. No
power-cut test exists. Ran, after the fixes: `norn-server`'s `crash`, `startup` and
`encryption` tests (which `kill -9` a daemon, including an encrypted one, and check
nothing acknowledged `DURABLE` is lost), and `norn-storage`'s `crash` tests.

**Shared memory.** Read: settings checks, `platform/unix.rs` and the start of
`telemetry/plane.rs`. The frame path was **not traced** in this review, and iceoryx2
itself was not audited. SECURITY.md's trust statement stands on its earlier analysis.

**Logs.** Whether client strings can inject log lines was **not examined**.

**Unsafe.** `git grep unsafe` across `crates`, `adapters` and `xtask`: the only `unsafe`
code in Norn's own source is `crates/transport/src/platform/windows/security.rs`. Its
blocks were read in part. The workspace denies `unsafe_code`. Unsafe in dependencies,
including runtime-rs, iceoryx2 and the RustCrypto crates, was not audited.

**Dependencies.** Ran `cargo deny --locked check` with the crypto crates added:
advisories, bans, licences and sources pass. It ignores `RUSTSEC-2024-0436` and
`RUSTSEC-2025-0134`, each with a reason in `deny.toml`; the second no longer matches any
crate and could be removed. Source of dependencies was not read, apart from what is named
above.

**Encryption.** Added after this review's fixes; design, exact coverage and the
tampering it does not detect are in [storage.md](../reference/storage.md#encryption).
Written by the same author as this review, it has had no independent review. Ran:
`crates/storage/tests/encryption.rs` and `encryption_keys.rs` (round trip, nothing in
the clear on disk, tamper with correct CRCs, swapped frames, wrong key, plain and
encrypted refused both ways, compaction and rekey rotation, a crash mid-rekey, a torn
encrypted tail, key file mode) and `crates/server/tests/encryption.rs` (restart, kill
and journal replay, wrong or no key changing nothing, verify reporting a forged chunk,
`norn rekey` end to end). Not run: Windows, and key handling under a debugger or a
core dump, where keys in memory are readable.
