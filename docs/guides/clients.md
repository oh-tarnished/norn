# Using Norn from your own code

Three ways in, all over the same public API: gRPC from your own program, `nornctl`
from a script, and MCP from an AI agent. None of them has a private door into
storage.

## gRPC

The Protobuf schema under [`protobuf/`](../../protobuf) is the API and its source of
truth. Services: `StreamService`, `EntityService`, `SignalService`, `TelemetryService`
(`AppendSamples`, `SubscribeEvents`), `QueryService`, `StateService`, `ReplayService`
and `AdminService`, plus the standard `grpc.health.v1`. Clients negotiate a protocol
version; this build speaks 1.8 (`norn_protocol::PROTOCOL_VERSION`).

A Rust client needs `norn-ipc` to dial the local endpoint and `norn-protocol` for the
generated stubs. The crates are not on crates.io; depend on the repository at a
release tag, such as `v1.0.0-rc.2`.
[`crates/cli/examples/plain_client.rs`](../../crates/cli/examples/plain_client.rs)
is a complete client with nothing of the daemon in it: it creates a stream, an entity
and a signal, and appends through a bounded channel. Captured from Norn 0.1.0:

```console
$ cargo run -p norn-cli --example plain_client -- unix:/tmp/norn-demo/t/norn/norn.sock
batch 1 reached ACKNOWLEDGEMENT_LEVEL_BUFFERED
batch 1 reached ACKNOWLEDGEMENT_LEVEL_DURABLE
```

A live device adapter should not start from scratch: `norn-sink` adds the bounded
buffer, retries and catalogue handling around that client
([writing a device adapter](device-adapter.md)). The steps a client must follow are in
[protocol, "Writing a client"](../reference/protocol.md#writing-a-client).

Any gRPC tool that speaks HTTP/2 over a Unix socket works too. From `1.0.0-rc.1`,
the daemon offers v1 and v1alpha server reflection on Unix sockets and named pipes,
so Postman can discover the methods without importing schemas. Reflection stays off
on TCP. For older daemons, give the tool a descriptor set built by `buf`. This
output was captured from Norn 0.1.0, which spoke protocol 1.6:

```console
$ buf build -o norn.binpb
$ grpcurl -plaintext -unix -authority localhost -protoset norn.binpb \
    -d '{"name":"server"}' /tmp/norn-demo/t/norn/norn.sock norn.admin.v1.AdminService/GetServer
{
  "name": "server",
  "serverVersion": "0.1.0",
  "protocolVersion": {
    "major": 1,
    "minor": 6
  },
```

(The response continues with capabilities, limits and recovery counters.) The
semantics of every method, error and acknowledgement level:
[protocol](../reference/protocol.md). Endpoints and the security model:
[IPC](../reference/ipc.md).

## nornctl

`nornctl` uses only the public API; it has no private door. The one exception is
offline: `nornctl restore` and `nornctl migrate` run with no daemon, so they open the
data directory themselves ([architecture](../reference/architecture.md#layers-and-the-dependency-table)).
Exit status is 0 on success, 1 when a command failed and 2 for a command line it
could not parse, so it scripts cleanly. Every command, with real output:
[nornctl](../reference/cli.md).

## MCP

The daemon serves 17 read-only tools generated by `protoc-gen-mcp` from the RPCs'
`(mcp.v1.tool)` annotations. Every tool calls the same gRPC API in process, through
runtime-rs's `HybridServer`. There is no separate `norn-mcp` executable.

For a client that starts its own daemon, use `norn --mcp stdio`. A Homebrew service
can enable MCP transports in its configuration; its default is off. MCP over loopback
HTTP has no authentication, so every local user can call it once it is on; a Unix
socket or named pipe keeps it to the daemon's user. Writes remain gRPC calls. Client
setup and transport details: [AI agents](ai-agents.md) and [MCP](../reference/mcp.md).
